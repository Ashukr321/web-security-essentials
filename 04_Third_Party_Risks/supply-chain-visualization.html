Key defense

Subresource Integrity (SRI)

Hash-verify every external script before the browser executes it. If the CDN is compromised, the script is blocked.

<script src="https://cdn.example.com/lib.js" integrity="sha384-oqVuAfXRKap7fdgc..." crossorigin="anonymous"></script>
1 Browser downloads the script from the CDN
2 Computes SHA-384 hash of the downloaded content
3 Compares with the integrity attribute value
4 Match → script executes. Mismatch → blocked (network error)
Defense layers

Supply chain hardening

L1

Lock files + npm ci

Pin exact versions with integrity hashes. npm ci in CI verifies hashes and fails on mismatch. Never npm install in production builds.

L2

Scoped packages + registry config

Use @company/pkg scoping. Set .npmrc to resolve private scopes from your private registry only — prevents dependency confusion.

L3

SRI for external scripts

integrity="sha384-..." on every <script> and <link> from CDNs. Browser blocks modified files.

L4

CSP (Content Security Policy)

Whitelist which domains can serve scripts. script-src 'self' https://trusted-cdn.com blocks injected scripts from unknown origins.

L5

Automated scanning

npm audit, Snyk, Socket.dev — detect known vulnerabilities, suspicious install scripts, and unexpected network access in dependencies.

L6

Pin CI actions by SHA

uses: actions/checkout@a1b2c3 not @v3. A tag can be moved to point at malicious code; a commit SHA is immutable.

Interview prep

Quick-fire questions

Compromising a dependency, tool, or third-party service that your application relies on — instead of attacking the application directly. The attacker's code runs with your application's privileges because it's loaded as a trusted component. The blast radius is massive: one compromised package can affect every application that depends on it.
An attacker publishes a public package with the same name as your private/internal package but with a higher version number. If your package manager checks both registries, it may prefer the higher version from the public registry. The fix: use scoped packages (@company/pkg) and configure .npmrc to resolve your scope exclusively from your private registry.
Subresource Integrity — a cryptographic hash in the integrity attribute of <script> or <link> tags. The browser computes the hash of the downloaded file and compares it. If the CDN serves modified content (compromised, injected, tampered), the hash won't match and the browser refuses to execute the script. It protects against CDN compromise and MITM modification of external resources.
npm ci installs from the lockfile exactly — no dependency resolution, no version range matching. It verifies integrity hashes for every package, deletes node_modules first (clean slate), and fails if package-lock.json is out of sync with package.json. npm install may resolve different versions, may not verify hashes, and can silently update the lockfile. In CI/CD, deterministic + verified = safe.
Everything your own JavaScript can do: read the entire DOM (form inputs, user data), access cookies (if not HttpOnly), make network requests to any server (exfiltrate data), modify the page (inject fake forms, redirect users), access localStorage/sessionStorage, register Service Workers for persistent control, and mine cryptocurrency. A third-party script runs with the same origin privileges as your own code. That's why CSP, SRI, and sandboxed iframes are critical.
A class of web-skimming attacks where card-stealing JavaScript is injected into e-commerce checkout pages. The injection comes via compromised third-party scripts (analytics, marketing, chat widgets) or tag managers. The skimmer captures payment form data (card number, CVV, expiry) and sends it to the attacker's server. The original payment still processes — neither the user nor the merchant notices. British Airways lost 380K cards in 15 days this way.
Three layers: (1) Use scoped packages — @company/auth-utils can't collide with unscoped public names. (2) Configure .npmrc to resolve your scope exclusively from your private registry: @company:registry=https://registry.internal.com/. (3) Claim your internal package names on the public registry as empty placeholder packages so attackers can't. Alex Birsan's research showed this affected Apple, Microsoft, and Tesla — it's a real and common gap.

Key takeaway: You don't control your dependencies — you trust them. Every npm package, CDN script, and build tool is an attack surface. Lock files pin versions, SRI verifies content, CSP limits execution, and scoped packages prevent confusion. The question isn't whether a supply chain attack will happen — it's whether your defenses catch it before it reaches production.
