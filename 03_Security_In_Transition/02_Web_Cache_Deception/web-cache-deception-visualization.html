SECURITY IN TRANSITION

Web Cache Deception

The cache and the origin speak different languages when reading a URL. Attackers exploit the gap to steal private data from the cache.

Click play to see the attack flow
The Core Problem

Path Confusion

The origin server and CDN cache interpret the same URL differently. That disagreement is the entire vulnerability.

Origin Server sees

/account/settings/nonexistent.css

Routes by path prefix. /account/settings/* matches. Ignores trailing segment. Serves the real account page with private data.

Cache / CDN sees

/account/settings/nonexistent.css

Classifies by file extension. Sees .css and decides it's a static asset. Stores the response for everyone. Serves it without authentication.

Attack Anatomy

How It Works

Five steps from crafted URL to stolen private data.

01

Attacker crafts a URL

Takes a real private endpoint like /account/settings and appends a fake static file: /account/settings/anything.css

02

Sends link to victim

Via phishing email, chat message, or embedded in a page. The victim clicks while logged in.

03

Origin serves private page

Server routing ignores the /anything.css suffix. Returns the victim's real account page with name, email, tokens.

04

Cache stores the response

CDN sees the .css extension, classifies it as a static asset, and caches the full response — including all private data.

05

Attacker retrieves cached data

Visits the same URL. No authentication needed — the cache serves the stored response. Victim's private data is now in the attacker's hands.

Techniques

Types of Path Confusion

Three ways attackers exploit the mismatch between how servers route and how caches classify.

Path Mapping

Server uses wildcard routing, cache uses extension matching. Extra path segments are ignored by one, trusted by the other.

/account/settings/fake.css

Delimiter

Different systems treat ; %00 ? as different things — path separator vs part of filename.

/account;x.css
/account%00x.css

Normalization

Server decodes %2f to / and resolves .. — cache stores the raw, encoded URL as the cache key.

/account/..%2fstatic/x.css

Context

Why "Security in Transition"?

This vulnerability doesn't exist in either component alone. It appears when you bolt a new layer onto an existing system.

Before CDN

User → Server
No cache, no deception possible. Same app code is safe.

→

After CDN

User → CDN → Server
Zero code changes, new attack surface. Cache and server disagree.

Same pattern as CORS (trust boundaries shifted), CSRF (stateful sessions + stateless requests), and HTTPS/HSTS (transport layer upgrade). The architecture changed but the security model didn't keep up.

Common Confusion

Deception vs Poisoning

They sound similar but the mechanism, goal, and fix are completely different.

Cache Deception Cache Poisoning
What's cached A real but private response A modified/malicious response
Goal Steal user data Serve malware or deface content
Who triggers Victim visits the crafted URL Attacker sends a poisoned request
Attack type Read attack Write attack
Root cause Path confusion between cache & origin Unkeyed input reflected in cached response
Defenses

How to Prevent It

Ranked from most effective to belt-and-suspenders.

01

Cache only known static paths

Don't cache by file extension. Whitelist exact directories: /static/*, /assets/*. Everything else passes through to origin.

02

Cache-Control headers

Every authenticated page must send Cache-Control: no-store, private. The origin explicitly tells the cache "don't store this."

03

Normalize URLs identically

Make the cache decode and resolve paths the same way the origin does before making caching decisions. Same input → same interpretation.

04

Strict routing — reject junk paths

If the server routes /account/settings and gets /account/settings/garbage.css, return 404 instead of serving the page.

Key Takeaway: Web Cache Deception works because caches and origin servers speak different languages when reading a URL. The cache sees a file extension and thinks "static." The server sees a route pattern and thinks "dynamic." The attacker exploits this to make the cache store private pages anyone can retrieve. Fix it: never let the cache guess — use Cache-Control headers and cache only known static paths.
