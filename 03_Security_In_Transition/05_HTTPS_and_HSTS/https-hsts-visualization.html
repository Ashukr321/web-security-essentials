TRANSPORT SECURITY

HTTPS & HSTS

HTTPS encrypts the channel. HSTS ensures the browser always uses it. Together they stop eavesdropping, tampering, and SSL stripping attacks.

The difference

HTTP vs HTTPS

HTTP (plain)

  • Traffic readable by anyone on the network
  • Data can be modified in transit (ad injection, malware)
  • No proof you're talking to the real server
  • Passwords, tokens, cookies sent in cleartext
  • ISPs can inject tracking headers

HTTPS (TLS)

  • All traffic encrypted end-to-end
  • Tamper-proof — any modification breaks the MAC
  • Server authenticated via certificate chain
  • Forward secrecy — past sessions safe if key leaks
  • Required for HTTP/2, service workers, many APIs
Under the hood

The TLS 1.3 handshake

One round trip to establish an encrypted connection. Everything after the handshake uses fast symmetric encryption.

1

ClientHello

Client sends supported TLS versions, cipher suites, and its ECDHE key share. In TLS 1.3 the key share is sent immediately — no extra round trip.

2

ServerHello + Certificate

Server picks cipher, sends its ECDHE key share and certificate. In TLS 1.3, the certificate is already encrypted — passive observers can't see which site you're connecting to.

3

Client verifies certificate

Browser checks: Is the cert signed by a trusted CA? Does the domain match? Is it expired or revoked? Any failure → connection blocked.

4

Session key derived

Both sides combine their ECDHE shares to derive the same symmetric key. This key never travels over the wire — even if recorded, the traffic can't be decrypted later (forward secrecy).

5

Encrypted HTTP traffic

All HTTP requests and responses are encrypted with AES-GCM or ChaCha20-Poly1305. Fast, authenticated, tamper-proof.

The attack

SSL stripping

A man-in-the-middle downgrades your connection from HTTPS to HTTP. You see a working page — just no padlock.

1

User types bank.com

Browser defaults to http://bank.com — plain HTTP. The first request is unencrypted.

2

Attacker intercepts the HTTP request

On the same WiFi (coffee shop, hotel, airport). Uses ARP spoofing or a rogue access point to sit between victim and router.

3

Attacker connects to bank over HTTPS

Attacker → bank.com is encrypted (HTTPS). But victim → attacker is plain HTTP. Attacker rewrites all https:// links to http://.

4

Victim submits login — in plaintext

The page looks real. No padlock, but most users don't check. Passwords, session tokens, card numbers — all visible to the attacker.

The defense

How HSTS stops SSL stripping

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

First visit (vulnerable)

Browser sends http://bank.com. Server 301-redirects to HTTPS. This first request is still vulnerable to stripping — the "first-visit problem."

Browser receives HSTS header

The HTTPS response includes Strict-Transport-Security. Browser stores: "bank.com is HTTPS-only for 1 year."

All future visits (protected)

User types bank.com → browser internally rewrites to https:// before any network request. Shows as 307 Internal Redirect in DevTools. No HTTP ever leaves the machine.

HSTS Preload (first visit protected too)

Domain added to the browser's built-in preload list. Even the very first visit goes to HTTPS. Shipped with Chrome, Firefox, Safari, Edge. Submit at hstspreload.org.

Common issues

HTTPS/HSTS vulnerabilities

Mixed Content

HTTPS page loads scripts/images over HTTP. Active mixed content (scripts) is blocked; passive (images) shows a warning. One HTTP resource breaks the entire security guarantee.

Weak TLS Config

TLS 1.0/1.1 enabled (BEAST, POODLE). Weak ciphers like RC4 or DES. Missing forward secrecy. Fix: TLS 1.3 only, AES-GCM + ChaCha20.

Short HSTS max-age

max-age=86400 (1 day) means the browser forgets after 24 hours. Attacker waits for expiry, then strips. Use at least 1 year.

Missing includeSubDomains

HSTS without includeSubDomains leaves http://sub.example.com open to stripping. Attackers use subdomains to set malicious cookies.

HSTS on HTTP Response

Browsers ignore HSTS headers received over HTTP — an attacker could inject them. HSTS only works when delivered over HTTPS.

Certificate Errors Ignored

Training users to click "Proceed anyway" on cert warnings defeats the entire chain of trust. HSTS with preload prevents even the option to bypass.

Best practices

Transport security checklist

L1

HTTPS everywhere

TLS 1.3, strong ciphers (AES-GCM, ChaCha20), forward secrecy (ECDHE). Redirect all HTTP → HTTPS with 301.

L2

HSTS with max-age ≥ 1 year

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

L3

HSTS Preload

Submit to hstspreload.org. Protects even the first visit. Removal takes months — commit fully.

L4

No mixed content

Use Content-Security-Policy: upgrade-insecure-requests to auto-upgrade HTTP subresources.

L5

Certificate Transparency

Ensure certs are CT-logged. Monitor CT logs for unauthorized certificates issued for your domain.

Interview prep

Quick-fire questions

Eavesdropping (encrypts traffic), tampering (authenticated encryption detects modification), and impersonation (certificate validates server identity). It does NOT protect against vulnerabilities in the application itself — XSS, SQL injection, etc. still work over HTTPS.
Forward secrecy (via ECDHE) means each session uses a unique key derived from ephemeral key pairs. If the server's private key is compromised later, past recorded sessions cannot be decrypted. Without it (plain RSA key exchange), an attacker who records traffic and later steals the key can decrypt everything retroactively. TLS 1.3 mandates forward secrecy.
A MITM attack where the attacker intercepts the initial HTTP request, connects to the server over HTTPS, and serves the victim an HTTP version of the page. The victim stays on HTTP (no padlock) while the attacker relays everything. All credentials and data travel in plaintext between victim and attacker. HSTS + preloading prevents this by ensuring the browser never makes the HTTP request.
HSTS is delivered via an HTTP response header. On the very first visit, the browser hasn't seen this header yet — so it may connect over HTTP first. This window is vulnerable to SSL stripping. The fix is the HSTS preload list: a hardcoded list of HTTPS-only domains compiled into every major browser. Once preloaded, even the first visit is protected.
TLS 1.3 removed insecure options (RSA key exchange, CBC ciphers, SHA-1, compression), requires forward secrecy, reduced the handshake from 2 round trips to 1, encrypts the server certificate (hiding which site you connect to from passive observers), and supports 0-RTT resumption for repeat connections. There are no known vulnerabilities in TLS 1.3 as of 2025.
An HTTPS page loading subresources over HTTP. Active mixed content (scripts, stylesheets, iframes) can be modified by a MITM to inject malicious code — browsers block it. Passive mixed content (images, audio, video) can leak information and be swapped — browsers warn but may allow it. Even one HTTP resource compromises the security of the entire page.
Not directly if configured correctly. Attack vectors: (1) SSL stripping before HSTS kicks in, (2) compromised or misissued CA certificate, (3) user clicking through certificate warnings, (4) TLS implementation bugs (rare), (5) client-side malware installing a root CA for interception. Corporate proxies use the last technique legally — they install their CA on managed devices.

Key takeaway: HTTPS encrypts the channel — but only if the browser actually uses it. HSTS ensures it does, and preloading covers the first visit. SSL stripping exploits the gap between typing a URL and reaching HTTPS. The fix: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload — and submit to the preload list.
