Fundamentals

What is an "Origin"?

An origin is scheme + host + port. Change any one part and it's a different origin.

Two request types

Simple vs Preflight requests

A "simple" request goes straight through. Everything else triggers a preflight OPTIONS check first.

S

Simple request — no preflight

Method is GET, HEAD, or POST. Only safe headers. Content-Type limited to text/plain, multipart/form-data, or application/x-www-form-urlencoded. Request is sent immediately — server processes it regardless. CORS only controls whether JS can read the response.

P1

Preflight — browser sends OPTIONS first

Triggered by: PUT/DELETE/PATCH, custom headers like Authorization, or Content-Type: application/json. Browser asks: "Is this allowed?" with Access-Control-Request-Method and Access-Control-Request-Headers.

P2

Server approves — actual request sent

If the preflight response includes the right Access-Control-Allow-* headers, the browser sends the real request. Access-Control-Max-Age caches the preflight so subsequent requests skip it.

P3

Server denies — request never sent

If the preflight fails (wrong origin, missing method), the browser never sends the actual request. This is the key difference from simple requests: preflight protects the server from even receiving the request.

Reference

CORS headers

Header Dir Purpose
Origin REQ Browser-set. Tells the server where the request came from
Access-Control-Allow-Origin RES Which origin can read the response (* or exact origin)
Access-Control-Allow-Methods RES Preflight: which HTTP methods are allowed
Access-Control-Allow-Headers RES Preflight: which custom headers are allowed
Access-Control-Allow-Credentials RES Whether cookies/auth can be included (can't use with *)
Access-Control-Expose-Headers RES Which response headers JS can read beyond the safe set
Access-Control-Max-Age RES How long (seconds) to cache the preflight result
Access-Control-Request-Method REQ Preflight: what method the actual request will use
Access-Control-Request-Headers REQ Preflight: what custom headers the actual request will send
Vulnerabilities

Common CORS misconfigurations

Each of these lets an attacker's site read authenticated responses from your API.

Reflected Origin

Server blindly echoes back whatever Origin header was sent. Any site can read authenticated data.

ACAO: ${req.headers.origin} ACAC: true
CRITICAL

Null Origin Allowed

Sandboxed iframes and data: URIs send Origin: null. Attacker crafts a page that exploits this.

ACAO: null ACAC: true
CRITICAL

Weak Regex

Checking endsWith("example.com") also matches evil-example.com. Partial matching = full bypass.

origin.endsWith("example.com") // evil-example.com ✓ (oops)
CRITICAL

Subdomain Wildcard

Allowing *.example.com trusts every subdomain. One subdomain takeover = full CORS bypass.

ACAO: *.example.com // stolen-sub.example.com ✓
HIGH

Wildcard + Credentials

Browsers reject * with credentials, but it signals the dev wanted full access — the real config may be worse.

ACAO: * ACAC: true // browser rejects
HIGH

Missing Vary: Origin

Without Vary: Origin, CDN caches one origin's ACAO header and serves it to all — cache poisoning.

// Cache stores ACAO: good.com // evil.com gets cached ACAO
HIGH
Defense layers

Configuring CORS correctly

L1

Explicit origin allowlist

Maintain a Set of allowed origins. Check with exact string match — never regex, never .endsWith().

if (ALLOWED.has(origin)) res.set('ACAO', origin)
L2

Always set Vary: Origin

When ACAO changes per request, Vary: Origin prevents CDN cache poisoning. Always include it.

res.set('Vary', 'Origin')
L3

Never allow null origin

Reject Origin: null outright. Sandboxed iframes and data URIs send it — all attacker-controlled.

L4

Minimize exposed surface

Only allow the methods and headers your API actually uses. Don't Allow-Methods: * or Allow-Headers: *.

L5

Credentials only when needed

Only set Allow-Credentials: true on endpoints that need cookies. Prefer token-based auth in headers.

Context

SOP vs CORS vs CSP

Same-Origin Policy

  • Browser default
  • Blocks cross-origin reads
  • Allows cross-origin writes (forms, links)
  • Allows cross-origin embeds (images, scripts, iframes)
  • No server config needed

CORS

  • Server opt-in to relax SOP
  • Controls which origins can read responses
  • Uses HTTP headers
  • Preflight for non-simple requests
  • Not a security feature — a permission system

CSP

  • Server directive for page behavior
  • Controls what the page itself can load
  • Restricts scripts, styles, images, frames
  • Mitigates XSS
  • Complementary to SOP/CORS
